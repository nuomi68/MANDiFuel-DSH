# 自适应优化、反演与顺序试验

`adaptive-study` 类必须使用本工作流：后续候选依赖已有响应的优化、参数反演、阈值搜索和顺序试验，或用户指定需保持生命周期的搜索算法。可以预先枚举且不要求算法更新的候选列表使用固定点工作流。

## 必经阶段

1. **固定方法**：定义变量、响应与约束，记录原生算法、初始化、种子、更新边界、停止条件和实际启动记录与用户明确限制（默认无次数上限）。反演还需目标观测、单位、残差及权重；阈值搜索需阈值方向、夹逼条件和有效单调性假设。
2. **绑定评价**：加载 Orchestrate 与 Conduct，构造共享 Study 的准备与推进响应；已有完整评价器通过 `evaluate=` 接入。第一次实际评价进入同一方法，不额外增加试跑。
3. **保持原生循环**：候选经 Study 评价后，才向原方法提交有效观测。顺序单目标 Optuna 且公共接口适用时必须用 `run_optuna`；其他方法使用原生回调或 `next_points(history)`，单点顺序依赖一个 worker。
4. **持久与恢复**：每个观测只提交一次，包括最后观测；保存方法状态、随机状态、待执行点和真实停止原因。中断读取原状态，不能用相同种子重建新实例冒充恢复。
5. **按目的完成**：优化报告正常评价支持的最好可行点；反演报告拟合参数、残差及达到的容差；阈值搜索报告已确认的有效夹逼区间。顺序试验报告实际设计与停止原因。预算耗尽或证据不足明确保留，不能把预算内最好点称作已证明收敛。

响应驱动概率采样另外遵守[概率设计](uncertainty-quantification.md)；后续点在原生方法中产生，不强行一次预列完整未来样本。

## 定义搜索

记录变量、单位、边界、目标方向、输入约束和求解响应约束、实际启动记录与用户明确限制（默认无次数上限）、算法、随机种子及停止条件。采用用户给定算法；未指定时选择适合问题与预算的具名方法，并记录理由和设置。

使用已有库的原生回调管理候选提议与更新。二分用于单调阈值或夹逼，不是一般最小化。初始化种群与后续更新都计入预算。

## 持久 Optuna 控制器

顺序单目标 Optuna 且以下接口适用时，必须使用公共控制器，确保响应绑定、待执行点与采样器状态可恢复；用户已有满足同一状态契约的控制器可直接复用：

```python
from study_runner import Study, run_optuna
import optuna

study = Study(ROOT, prepare=prepare, command=['bash', 'run.sh'],
              progress=extract_progress, end_time=requested_end_time)
optimizer = run_optuna(
    study,
    suggest=lambda trial: {
        'a': trial.suggest_float('a', -0.2, 0.2),
        'b': trial.suggest_float('b', -0.15, 0.15)},
    objective=lambda point, response: response['fuel_max_T_K'],
    budget=12,
    sampler=optuna.samplers.TPESampler(seed=20261018, n_startup_trials=4))
```

参数和目标键仅为示例，按任务绑定。控制器管理点ID和trial序号，`suggest` 只返回参数。检查点是当前任务自己生成的可信pickle，不读取下载或来源不明的检查点。重复运行恢复原生优化器、采样器随机状态和待执行点，不重复请求参数。

正常求解后提取失败时就地修复读者再继续，不从观察表重新创建采样器。求解失败时暂停当前控制器以便诊断，按输入恢复闭环修复后继续研究；相同失败输入不自动原样重试。一个研究根使用一个控制器进程，归档时保留检查点。这里的 `budget` 是目标试验数，真实启动单独记账；只有用户明确设置上限时才按上限停止。

## 定制原生目标回调

仅当公共 `run_optuna` 不能表达用户要求的目标、执行协议或原生算法时采用本节；先记录具体缺口。不能为了省略持久状态而改用手写循环。已有受信控制器直接复用。先绑定准备与推进响应，按以下形式让库管理 trial 生命周期，并补齐所需持久状态：

```python
study = Study(ROOT, prepare=prepare, command=['bash', 'run.sh'],
              progress=extract_progress)

def objective_trial(trial):
    point = {**suggest(trial), 'id': str(trial.number)}
    record = study.run([point], workers=1)[-1]
    if record['status'] != 'completed' or record.get('response') is None:
        raise RuntimeError(f'评价需要修复：{record}')
    return objective(point, record['response'])

optimizer.optimize(objective_trial, n_trials=budget, n_jobs=1)
```

完整评价器使用 `Study(ROOT, evaluate=evaluate)`。目标返回后优化器才提交trial，完成态、时间和最好值在trial后回调或 `optimize` 结束后汇总。Optuna的活动 `Trial` 用于建议参数与属性，完成的 `FrozenTrial` 提供 `state`、`value`/`values` 和时间。`best_value` 要求已有完成的单目标trial，多目标使用 `best_trials`。

报告生成放在目标回调之外。示例把失败暴露出来以便修复；需要继续搜索时必须明确失败策略和记录。外部调度或种群更新需要跨越trial生命周期时，可使用ask/evaluate/tell。第一次真实评价属于这个同一优化循环，不额外先跑验证点；成功返回直接推进原有方法实例。

中断恢复同时恢复采样器状态和trial历史。用同一种子创建新采样器再打开数据库不等于恢复内存状态。按[预算区别](study-runner.md#点调度与预算)核算剩余实际启动，并从 `optimizer.trials` 等原生历史导出完成元数据。

## 方法适用范围

只有一个连续有界变量且接受局部或单峰假设时，使用有界黄金分割或Brent类搜索。否则限定为预算内最佳观察结果，或使用明确的有限、多起点设计。

整个搜索在一个任务Python控制器中运行。库已经管理提议和更新时复用其循环；需要就绪集合或种群分派时使用 `next_points(history)`，空列表表示停止。每个观测更新一次，结束时把最后未消费的观测交给方法并保存原生状态及真实trial元数据。

仅在中断恢复且无法加载状态时才从有序历史重建；回放时间不是原trial时间。记录初始化、并列规则、更新顺序和停止规则；种群方法保留种群数和代数的算法含义，输入修复单独记账。同步一代在所需成员记录完整后更新，Study按配置workers调度未见成员。

有限离散域全部列出时使用候选选择。自适应整数、类别和混合变量使用能提出合法值的方法；不能把连续建议静默取整，编码、修复和重复规则都属于算法设置。

代理或贝叶斯搜索还需记录初始设计、代理模型、采集准则、种子及更新频率。预测与采集值不是物理求解结果，报告的最佳设计必须有真实有效评价。

## 失败、重复和交付

保留请求算法的提议及重复语义。确定性重复点是否共享求解是显式研究策略，不能擅自增加缓存；随机响应记录复测种子、次数和聚合。累积历史保留提议、启动、失败、目标与约束。

明确顺序、同步批次或异步更新，仅声明的顺序影响后续候选；恢复不能静默重新建议已完成点。失败惩罚是算法记账，不能充当物理响应；失败启动仍计预算。

交付已观察的最佳可行点和实际启动数。预算有限的无导数研究不证明全局最优或收敛；相邻可行/不可行点只有在所需单调性已经建立时才能夹定整体可行边界。

## 多目标

只对有效可行结果计算非支配关系，保留全部并列设计。每个目标独立记录方向和单位。标量化需要用户给出的权重与尺度；否则报告已观察的Pareto集合及权衡。
